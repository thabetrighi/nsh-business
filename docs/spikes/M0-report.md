## M0.2 — جرد القدرات

### ما يناسب المشروع
- **Rust تطبيق كامل على كل المنصات** بما فيها iOS وAndroid والويب (`libnsh.so` على Android، `nsh.wasm` على الويب). لا حاجة لـ TSX في المنتج.
- **مكونات `nsh-base` غير مصمّمة (unstyled)** تملك الحالة والتركيز ولوحة المفاتيح والإتاحة: Button, Input, NumberInput, Select, Combobox, Checkbox, Radio, Switch, Toggle, Dialog, AlertDialog, Sheet, Popover, Menu, Tooltip, Toast, Tabs, NavStack, Accordion, Command (لوحة الأوامر), **DataTable**, Table, Tree, Pagination, DatePicker, Calendar, TimeField, OtpInput, Resizable, Toolbar, Dock, Plot (رسوم بيانية), Progress, Slider, Avatar, Carousel, Editor, RichEditor.
  - هذا يغطي معظم M3 (Design System): نبني طبقة التنسيق فقط.
- **قوائم افتراضية** (`List`) ورسم `Canvas` وعرض ويب `WebView`.
- **السمات (Theme)** بنمط shadcn/ui (`cssVars`)، مع فاتح/داكن.
- **المهام الخلفية:** `spawn` للمهام غير المتزامنة، و`background`/`blocking` تعمل على خيوط في المنصات الأصلية → مناسب لتشغيل SQLite خارج الخيط الرئيسي.
- **ملفات سطح المكتب:** `pick_paths`, `pick_save_path` (للتصدير والاستيراد والنسخ الاحتياطي).
- **الشبكة:** `fetch` ومؤقتات على كل المنصات.

### الحدود والمخاطر المكتشفة
| الحد | الأثر على المشروع | المعالجة |
|---|---|---|
| لا واجهة تخزين/قاعدة بيانات في NSH | متوقع | SQLite عبر crate مستقل (M0.3) |
| الويب **خيط واحد**، ولا ذكر لـ Web Workers | SQLite-WASM ثقيل قد يجمّد الواجهة | قياس في M0.4؛ عمليات قصيرة أو تقسيم العمل |
| الويب: OPFS غير موثّق، IndexedDB عبر `web-sys` فقط | يحدد خيار تخزين الويب | M0.4 |
| الويب: إعادة ترتيب النص ثنائي الاتجاه محدودة باتجاه الفقرة | النص المختلط على الويب قد يختلف عن Linux | اختبار في M0.5 على الويب |
| الويب: المكونات الأصلية تبقى فارغة | لا كاميرا/أجهزة أصلية على الويب | متوقع في PRD (وسيط محلي) |
| `open_path`/`move_to_trash` لسطح المكتب فقط | — | لا يؤثر |
| تحديثات Rust تعيد البناء وإعادة التشغيل (لا hot reload) | بطء التطوير نسبياً | مقبول |

## M0.3 — SQLite والأداء

المصدر: `spikes/m0-sqlite` (`cargo run --release`). مكتبة `rusqlite 0.37` (SQLite مضمّنة `bundled`)، WAL، FTS5 بمحلّل `unicode61 remove_diacritics 2` وفهارس بادئات 2 و3 أحرف.

| القياس (100 ألف منتج) | الوسيط | p95 | هدف PRD |
|---|---|---|---|
| إدخال 100k منتج + باركود + رصيد + فهرسة FTS | 0.87–0.97 ث | — | — |
| بحث عربي كلمة كاملة `حليب` | 3.26 ms | 3.74 ms | < 150 ms ✅ |
| بحث عربي بادئة `حلي*` | 3.07 ms | 4.70 ms | ✅ |
| بحث مركب `حليب Ifri` | 0.96 ms | 1.39 ms | ✅ |
| بحث لاتيني بادئة `Cev*` (نتائج كثيرة) | 5.78 ms | 10.51 ms | ✅ |
| بحث SKU | 0.13 ms | 0.18 ms | ✅ |
| بحث باركود دقيق | 0.01 ms | 0.02 ms | ✅ |
| `CompleteSale` ذرية، `synchronous=NORMAL` | 0.13 ms | 0.26 ms | < 200 ms ✅ |
| `CompleteSale` ذرية، `synchronous=FULL` | 0.41 ms | 0.75 ms | < 200 ms ✅ |
| رفض `operation_id` مكرر (UNIQUE) | ✅ | | |
| الرصيد = الافتتاحي + مجموع الحركات بعد 500 بيع | ✅ صفر اختلاف | | |
| حجم القاعدة | 45.3 MB | | |

**القرارات المقترحة (تدخل ADR-0002):**
- `rusqlite` مع `bundled` (نفس نسخة SQLite على كل المنصات، FTS5 مضمّن).
- `synchronous=FULL` للقاعدة التشغيلية: الفرق 0.3 ms مقابل ضمان عدم فقد آخر بيع عند انقطاع الكهرباء.
- البحث FTS5 مع بادئات؛ لا حاجة لمحرك بحث خارجي.
- **تحفّظ:** القياس على قرص خادم سريع. أقراص الهواتف الرخيصة أبطأ في fsync؛ يُعاد القياس على Android في M0.7. الهامش كبير (×250) فالخطر منخفض.
- ملاحظة: `remove_diacritics` يزيل التشكيل، لكنه لا يوحّد الهمزات (أ/إ/آ/ا) ولا التاء المربوطة/الهاء. يُضاف عمود "اسم مطبَّع" للبحث في M5.10.

### الويب: النص ثنائي الاتجاه (bidi)

بُني الويب في GitHub Actions (`web-spike.yml`) وصُوِّر في Chrome دون واجهة. قارنّا أربع لوحات على Linux والويب:

| اللوحة | Linux | الويب |
|---|---|---|
| RTL دون معالجة | ✅ | ❌ رمز لاتيني ملتصق بنص عربي ينكسر: `1L` يظهر `L…1` |
| RTL + `writing_direction(Rtl)` | ✅ | ❌ لا أثر للخاصية على الويب |
| RTL + عزل المقاطع اللاتينية/الرقمية بـ FSI/PDI | ✅ | ✅ الترتيب صحيح لـ `1L` والأقواس |
| LTR | ✅ | ❌ نفس كسر `1L` |

الصور: `img/m0-5-bidi-variants-linux.png` و`img/m0-5-bidi-variants-web.png`.

هذا يطابق ما توثقه NSH: على الويب «إعادة الترتيب ثنائي الاتجاه محدودة باتجاه الفقرة».

**المعالجة المعتمدة:**
- مكوّن نص في `nb-ui` يعزل تلقائياً المقاطع ذات الاتجاه المخالف بـ FSI/PDI، اعتماداً على تصنيف Unicode Bidi الصحيح (crate `unicode-bidi`)، لا على نطاق الحروف العربية فقط كما في هذا النموذج.
- تنسيق الأرقام والمبالغ والتواريخ في `nb-i18n` يُخرج نصاً معزولاً جاهزاً.
- اختبار لقطات شاشة للويب في CI لكل شاشة رئيسية.
- فتح Issue لدى NSH بالمشكلة مع النموذج (بعد موافقة المالك).

**الخلاصة المرحلية:** RTL ممتاز على Linux. على الويب التخطيط سليم والنص المختلط يحتاج طبقة عزل؛ الخطر متوسط ومعالجته واضحة.
